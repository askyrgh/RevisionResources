01 Internet Protocol (IP) Networking
⟳ Foundation for everything — load balancers, DNS, and CDNs all operate on top of IP. Know this before all other networking topics.
Core Concept

IP is the internet's postal system. It defines how to label a data packet with "from" and "to" addresses, and how that packet hops between routers until it reaches its destination. IP does its best to deliver — but makes no guarantee. This is called best-effort delivery.

Every device on a network gets an IP address — a unique numerical label — so other devices know where to send data.

Why It Matters

Before load balancers, DNS, or APIs, you need this baseline: how does data get from Server A to Client B? IP is the layer underneath all of that. It rarely gets asked about directly at mid-level, but it's the foundation for questions about latency, CDNs, and networking trade-offs.

Key Mechanics
  • IPv4 — 32-bit address (e.g. 192.168.1.1), ~4.3B addresses, now exhausted
  • IPv6 — 128-bit address, effectively unlimited
  • NAT — lets many private-IP devices share one public IP
  • TTL — countdown on each packet; hits 0 → dropped, prevents infinite loops
  • Connectionless — no handshake, no ordering, no delivery guarantee
Trade-offs
ChoiceProsCons
IPv4Universal support, simpleExhausted, needs NAT
IPv6Unlimited addresses, no NATLegacy support gaps
NATSolves address shortageBreaks true end-to-end, complicates P2P
Real World
  • Every HTTP request — browser resolves domain → IP via DNS → TCP over IP → HTTP
  • Load balancers route at the IP level (L3/4)
  • CDNs use anycast to route users to the nearest server
Interview Angle
Likely prompt shape "How does a request travel from client to server?" → DNS resolution → IP address → TCP handshake → HTTP request. State this chain confidently and briefly.
Key distinction to know L4 load balancing works at the IP/TCP level (routes on IP + port). L7 works at the HTTP level (routes on URL, headers). This distinction flows directly from understanding where IP sits in the stack.
Quick Revision Recap
IP = addressing + routing. Best-effort, connectionless, unreliable delivery of packets.
IPv4 (32-bit, exhausted) vs IPv6 (128-bit, near-unlimited). NAT bridges public ↔ private.
Packets carry source IP, dest IP, TTL. TTL prevents infinite routing loops.
Reliability is NOT IP's job — that's TCP's job, sitting on top of IP (hence "TCP/IP").
Shows up indirectly: DNS → IP → TCP handshake → HTTP; and in L4 vs L7 load balancing.
⟳ OSI is vocabulary, not implementation. You need it to reason about where any component in your architecture operates — especially L4 vs L7 load balancers.
Core Concept

The OSI model breaks down "how data travels between devices" into 7 stacked layers, each with a distinct job. It's a mental model for reasoning about where a problem or technology sits in the stack — not something you implement directly. Real-world networking follows the simpler 4-layer TCP/IP model instead.

Mnemonic: Please Do Not Throw Sausage Pizza Away

The 7 Layers
#LayerJobExamples
7ApplicationWhat the app/user interacts withHTTP, DNS, gRPC
6PresentationEncoding, encryption, compressionTLS/SSL, JSON serialization
5SessionEstablish/maintain/teardown sessionsSession tokens
4TransportEnd-to-end delivery, reliability, portsTCP, UDP
3NetworkRouting, logical addressingIP, routers
2Data LinkNode-to-node, local networkEthernet, MAC, switches
1PhysicalRaw bits over a mediumCables, radio waves
OSI vs TCP/IP Model

Real-world stacks follow TCP/IP's 4-layer model (Application, Transport, Internet, Link). TCP/IP squashes OSI's Layers 5-7 into one Application layer — in practice, session/presentation concerns are handled inside the application protocol.

Encapsulation

Each layer wraps the layer above in its own header. This is why data gets different names per layer: IP packet (L3), TCP segment (L4), Ethernet frame (L2).

Real World
  • L4 Load Balancer — routes on IP + port only, fast, no content awareness
  • L7 Load Balancer — reads actual HTTP content (URL, headers), smarter routing
  • WAF (Web App Firewall) — operates at L7, inspects HTTP content
  • TLS/SSL — conceptually L6 (Presentation), sits between Transport and Application
Interview Angle
Highest-yield fact L4 vs L7 load balancing. If you say "we'll put a load balancer here," expect the follow-up: "L4 or L7, and why?" L4 = fast, no content awareness. L7 = can route on URL paths, headers, cookies — used for microservice routing, A/B testing.
Don't over-invest Memorizing all 7 layers with textbook precision isn't the goal. Focus on L3 (IP), L4 (TCP/UDP), and L7 (HTTP) — those are the three that appear in real system design conversations.
Quick Revision Recap
7 layers (top to bottom): Application → Presentation → Session → Transport → Network → Data Link → Physical.
Real-world stacks follow TCP/IP (4 layers). OSI is vocabulary, TCP/IP is the reality.
Encapsulation: each layer adds a header going down (packet → segment → frame).
L3 = IP (routing) · L4 = TCP/UDP (reliability, ports) · L7 = HTTP (what you build as a backend dev).
Key interview fact: L4 LB = IP/port routing, fast. L7 LB = HTTP-aware, smarter, more overhead.
⟳ Both sit at L4, on top of IP. Your protocol choice shapes your whole architecture — retries, packet loss tolerance, and latency all follow from it.
TCP

Like a phone call. Both sides confirm the connection first (three-way handshake), data arrives in order, and anything garbled is retransmitted automatically. Reliable, ordered, with overhead.

Three-Way Handshake

SYN → SYN-ACK → ACK. Adds latency but ensures both sides are ready before data flows.

Head-of-line blocking

One lost packet blocks everything behind it, even if those packets already arrived. TCP's main weakness for time-sensitive data.

UDP

Like sending postcards. Fire-and-forget — no confirmation the other side is listening, no ordering guarantee, no retransmit. Fast, no overhead, no guarantees.

App-level reliability

If you need some reliability, build it yourself on top of UDP — e.g., only retransmit the most recent frame, not old ones. Smarter than TCP's blind retransmission for video.

QUIC / HTTP3

Built on UDP, reimplements reliability without TCP's head-of-line blocking. Worth name-dropping to sound current.

Trade-offs
TCPUDP
ReliabilityGuaranteed, orderedNo guarantees — packets can be lost, duplicated, out of order
SpeedSlower (handshake, ACKs, retransmits)Faster (fire-and-forget)
OverheadHigher (larger header, connection state)Minimal (small header, stateless)
Head-of-line blockingYes — one lost packet stalls everything behind itNo — each packet is independent
Best forHTTP, file transfers, databases, emailVideo/voice calls, gaming, DNS
Interview Angle
Always justify the choice Don't just say "TCP" or "UDP" — say why. "I'd use UDP here because occasional data loss is acceptable and low latency matters more than perfect delivery, like in a live video stream." The reasoning is what gets credit.
Common trap Don't say "TCP is just better." Reliability isn't free. Choosing TCP for a live video call would make the experience worse — the call would freeze waiting to retransmit old frames nobody needs anymore.
Quick Revision Recap
Both are L4 protocols on top of IP. Both use ports to reach the right process on a machine.
TCP: handshake, reliable, ordered, flow/congestion control → higher overhead, higher latency.
UDP: connectionless, no guarantees → minimal overhead, low latency. No head-of-line blocking.
TCP: HTTP, file transfer, databases. UDP: video/voice, gaming, DNS queries.
Always justify protocol choice via the speed vs reliability trade-off, not just naming it.
⟳ DNS uses UDP for speed (callback to TCP/UDP), and is the first step in the request path before any load balancer or CDN is involved.
Core Concept

DNS is the internet's phonebook — translating google.com into 142.250.194.46. It's a distributed hierarchy of servers, each responsible for a piece of the puzzle, with aggressive caching at every layer to keep it fast.

Lookup Flow
  • Browser checks its own cache first
  • If miss → asks a DNS resolver (ISP or public: 8.8.8.8, 1.1.1.1)
  • Resolver queries: Root → TLD (.com) → Authoritative server
  • Authoritative server returns the actual IP
  • Resolver caches, returns to browser, browser caches
  • Browser now has an IP and starts the TCP handshake
Key Record Types
  • A — domain → IPv4 address
  • AAAA — domain → IPv6 address
  • CNAME — domain → another domain (alias)
  • MX — domain → mail server
  • TTL — cache lifetime for any record
TTL Trade-off

High TTL = fewer lookups, less load, but slow propagation of IP changes. Low TTL = fast propagation, more lookups.

Trade-offs
ChoiceProsCons
Round-robin DNSSimple load balancingNo health checks, can hit dead servers
GeoDNS / AnycastRoutes to nearest server, low latency worldwideMore infrastructure to manage
High TTLFewer lookups, less loadSlow to propagate IP changes
Low TTLFast failover, fresh dataMore lookups, more load on DNS infra
Real World
  • Round-robin DNS — cycles through multiple IPs, crude load balancing
  • GeoDNS / Anycast — same domain, different IPs per region — core to CDN low latency
  • DNS-based failover — reroute around dead servers (slower than a LB due to TTL caching)
  • Runs mostly over UDP for speed — callback to TCP/UDP topic
Interview Angle
Good opener for any "design X" answer "A client resolves our domain via DNS to get an IP, then connects." Saying this shows you understand the full request path, not just the app logic inside your system.
Migration risk question "What happens if you change your server IP?" → Answer: DNS records with high TTL mean some clients keep hitting the old IP until TTL expires. Pre-lower your TTL days before a planned migration.
Trap Don't conflate DNS load balancing with a real load balancer. DNS has no health checks and can't do real-time traffic shaping.
Quick Revision Recap
DNS = distributed hierarchical lookup: Root → TLD → Authoritative server → IP.
Recursive resolver (ISP or 1.1.1.1) does the hopping and caches results at every layer.
TTL = cache duration. High TTL = less load, slow propagation. Low TTL = fast propagation, more lookups.
Record types: A (IPv4), AAAA (IPv6), CNAME (alias), MX (mail).
GeoDNS / Anycast = route users to nearest server. Core to CDN delivery. Runs over UDP.
⟳ Every load balancer is a reverse proxy (Proxy topic). The L4 vs L7 distinction maps directly to OSI layers. This is the bridge from "one server" to distributed system thinking.
Core Concept

A load balancer is a traffic cop sitting in front of multiple backend servers, deciding which server handles each request. This is what makes "just add more servers" (horizontal scaling) actually work — without it, all traffic would still hit one machine.

L4 vs L7 (callback to OSI)
L4 Load Balancer

Routes on IP + port only. Doesn't look at request content. Very fast, low overhead — but "dumb." Use when speed matters more than routing intelligence.

L7 Load Balancer

Understands the actual HTTP request — URL path, headers, cookies. Can route /api/video to video servers and /api/checkout to checkout servers. More overhead, far more flexible.

Routing Algorithms
  • Round Robin — cycle through servers in order, simple
  • Weighted Round Robin — bigger servers get more requests
  • Least Connections — send to server with fewest active connections
  • IP Hash — same client → same server (session affinity)
  • Random — surprisingly decent at scale
Health Checks

Periodic pings to a /health endpoint. Failed servers pulled from rotation automatically — what makes LBs smarter than DNS round-robin.

Trade-offs
ChoiceProsCons
L4Fast, simpleNo content-aware routing
L7Flexible, smart routingSlower, more resource-intensive
Round RobinDead simpleIgnores actual server load
Least ConnectionsAdapts to real loadSlightly more state to track
IP Hash (sticky)No shared session store neededServer death loses session, uneven load
Single LBSimpleSingle point of failure
Real World
  • NGINX / HAProxy — common software LBs, L7-capable
  • AWS ALB (L7) vs NLB (L4) — names map directly onto OSI
  • LBs also handle TLS termination — decrypt HTTPS once, plain HTTP internally
Preferred modern pattern

Stateless servers + shared session store (Redis) over sticky sessions. Removes the session-affinity problem entirely and is more scalable.

Interview Angle
Don't just draw a box Say why (distributes load, avoids SPOF, enables horizontal scaling) and what kind (L4 vs L7, which algorithm, with reasoning).
Expect these follow-ups "What if the load balancer dies?" → redundant pair / failover. "How do you handle sessions?" → stateless servers + Redis vs sticky sessions (IP hash) — prefer the former.
Quick Revision Recap
LB distributes requests across backend servers → horizontal scaling, removes single-server bottleneck.
L4 = IP/port routing, fast, dumb. L7 = HTTP-aware, smarter, more overhead.
Health checks dynamically remove dead servers — smarter than DNS round-robin.
TLS termination: LB decrypts HTTPS, talks plain HTTP internally. Offloads crypto from app servers.
Single LB = SPOF. Always mention redundant LB pairs in your design.
Prefer stateless servers + Redis over sticky sessions for better scalability.
⟳ Clustering is what makes the "multiple servers" behind a load balancer coordinate, detect each other's failure, and take over work — the coordination layer underneath availability.
Core Concept

Clustering groups multiple machines (nodes) to act as a single logical system, coordinating and covering for each other's failures. Where a load balancer decides which server gets a request, a cluster is the coordinated group itself — aware of peers, detecting failures, taking over work.

Cluster Types
Active-Passive

One node active, standby(s) idle, heartbeat triggers failover. Simple, predictable. Wastes standby resources.

Active-Active

All nodes serving simultaneously. Better utilization, no failover delay. Much harder — needs real-time state sync.

Leader Election & Split-Brain
Leader Election

Nodes agree on who's primary via consensus algorithms (Raft, Paxos) or tools like ZooKeeper/etcd — don't hand-roll this yourself.

Split-Brain

Network partition → two nodes both think they're leader → both accept writes → data diverges. Prevented via quorum (majority must agree) and fencing (cut off the old node's access before promoting a new leader).

Heartbeats

Periodic "I'm alive" pings. Missing several → failover triggered.

Frequency trade-off

Frequent = fast detection, but overhead + false positives on temporary blips. Infrequent = less overhead, slower detection, longer downtime.

Trade-offs
ChoiceProsCons
Active-PassiveSimple, predictableIdle resources, slight failover delay
Active-ActiveNo idle waste, no failover delayReal-time state sync is hard, conflict resolution needed
Quorum-basedPrevents split-brainMinority partition becomes unavailable
Interview Angle
Expect this follow-up "What happens if your primary database dies?" → standby promoted via heartbeat-based detection, with quorum to prevent split-brain. If you say "backup server" without explaining how it knows the primary is dead — that's the next question.
Good judgment signal Say you'd use a battle-tested coordination tool (ZooKeeper, etcd) rather than hand-rolling leader election. Reflects real engineering judgment.
Quick Revision Recap
Clustering = grouping nodes to act as one system, for scaling and failure resilience.
Active-Passive (standby + heartbeat failover) vs Active-Active (all serving, harder sync).
Leader election via Raft/Paxos or tools like ZooKeeper/etcd — don't build your own.
Split-brain: partition → two leaders → data diverges. Fix: quorum + fencing.
Real tools: etcd/ZooKeeper (coordination), Kubernetes (cluster management), Redis Sentinel (failover).
⟳ Caching is the first lever before heavier solutions like sharding. CDNs are caching at the geographic level — same TTL and invalidation concepts apply there too.
Core Concept

Caching stores a copy of data somewhere faster to access than its original source, so repeated requests skip expensive work. It exploits the fact that a small "hot" subset of data drives most requests — cache that, and you dramatically cut load on slower systems.

Caching Strategies
Cache-Aside (most common)

App checks cache first. On miss, fetches from DB and populates cache. Cache fills with what's actually requested.

Write-Through

Every write goes to cache + DB synchronously. Always consistent, but slower writes.

Write-Behind (Write-Back)

Write to cache immediately, DB updated async. Very fast writes, risk of data loss on cache crash.

Invalidation & Eviction
Invalidation ("one of the two hard problems in CS")
  • TTL — auto-expiry; risk of thundering herd on mass expiry
  • Explicit — actively delete on data change
  • Event-based — data change publishes event triggering invalidation
Eviction Policies
  • LRU — evict least recently used (default)
  • LFU — evict least frequently used
  • FIFO — evict oldest entry
Trade-offs
ChoiceProsCons
Cache-AsideSimple, resilient to cache failureCold miss on first request, possible staleness
Write-ThroughAlways consistentSlower writes, caches unread data
Write-BehindVery fast writesRisk of data loss, more complex
Short TTLFresher dataMore misses, more DB load
Long TTLBetter hit rateStaleness risk
In-memory (per server)Extremely fastNot shared across servers, inconsistent results
Distributed (Redis)Shared view, consistentNetwork hop (still far faster than DB)
Interview Angle
Proactively suggest caching In any "design X" answer with read-heavy traffic, add a cache layer without being prompted. Doing this unprompted is a strong signal. Always name the strategy: "cache-aside since reads vastly outnumber writes and we can tolerate slight staleness."
Thundering herd If a popular cache key expires, all simultaneous requests miss and hit the DB at once. Fix: jittered TTLs (randomize expiry) or single-flight locking (only one request refetches, others wait). Have this ready.
Trap Don't present caching as "free." Always mention the staleness trade-off — that's exactly what the interviewer is probing for.
Quick Revision Recap
Caching = faster-access copy of data. Exploits hot-data skew — small % of data drives most requests.
Layers: browser → CDN → app-level → distributed cache (Redis/Memcached) → DB's own cache.
Strategies: Cache-Aside (most common, lazy), Write-Through (consistent, slow), Write-Behind (fast, risky).
Invalidation: TTL, explicit, event-based. Always a freshness vs load trade-off.
Thundering herd: mass expiry → DB hit storm. Fix with jittered TTLs or single-flight locking.
⟳ CDN = caching + geographic distribution. Uses Anycast/GeoDNS (from DNS topic) for routing. Edge nodes are reverse proxies (from Proxy topic) that also cache.
Core Concept

A CDN is a globally distributed network of edge servers that cache and serve content physically close to the user. Latency has a hard floor set by the speed of light — no server optimization fixes the fact that data takes time to travel across the globe. CDNs solve this by moving the data closer.

Think of it as caching, geographically distributed — all the same TTL and invalidation concepts apply, with physical distance as the extra dimension being optimized.

Pull vs Push CDN
Pull CDN (most common)

Edge fetches from origin on-demand (cache-aside, geographically distributed). Cache fills based on real demand. Cold miss for first request per region.

Push CDN

Content proactively uploaded to edges ahead of demand. No cold-start. Useful for scheduled popular content (major video release). Requires predicting what's popular.

Origin Shield

Extra layer between edge nodes and origin. If many edge nodes miss at once, they hit the shield first — only the shield talks to origin. CDN-specific answer to thundering herd.

What Gets Cached
  • Static content — images, CSS, JS, video. Classic CDN use case. Rarely changes, cache a long time.
  • Dynamic content — personalized pages, API responses. Harder to cache, but CDNs can accelerate connections and terminate TLS close to the user even when content can't be cached.
TLS at the Edge

HTTPS terminated at the nearest edge node — same concept as load balancer TLS termination. The expensive handshake happens over a short distance.

Interview Angle
Trigger condition Any mention of "global users," "worldwide," or "media/static assets" → bring up CDN proactively. Frame it as "geographically distributed caching using the same TTL/invalidation concepts" — not a separate idea.
Trap Don't present a CDN as a solution for highly personalized/dynamic content — it shines on static and cacheable workloads. Be ready to say this explicitly.
Bonus point CDNs also naturally absorb DDoS traffic by distributing it across many edge nodes before it reaches origin.
Quick Revision Recap
CDN = geographically distributed edge caching. Cuts physical-distance latency that no server optimization can fix.
Routing to nearest edge via Anycast / GeoDNS — callback to DNS topic.
Pull CDN (on-demand, common, cold-start per region) vs Push CDN (pre-loaded, prediction-based).
Origin Shield: extra layer to protect origin from simultaneous cache-miss storms.
Common real pairing: object storage (S3) + CDN (CloudFront) for cheap, fast global media delivery.
⟳ Load balancers ARE reverse proxies. CDN edge nodes ARE reverse proxies. This topic ties them together — understanding this means you can classify any intermediary in a design.
Forward Proxy

Represents the client. The destination server sees the proxy, not the real client.

  • Client → Proxy → Internet
  • Hides client identity from destination
  • Uses: anonymity, content filtering, outbound caching
  • Deployed by: client's organization (e.g. corporate IT)
  • Example: corporate web filter, VPN (conceptually)
Reverse Proxy

Represents the server. The client sees the proxy, not the real backend.

  • Internet → Proxy → Backend servers
  • Hides backend topology from clients
  • Uses: load balancing, TLS termination, caching, rate limiting
  • Deployed by: service/application owner
  • Examples: NGINX, load balancer, CDN edge node
Side-by-Side Comparison
Forward ProxyReverse Proxy
RepresentsThe clientThe server
Hidden from whomServer doesn't see the real clientClient doesn't see the real server
Typical deployerClient's organizationService/application owner
Classic examplesCorporate content filterLoad balancer, CDN edge, NGINX, API Gateway
API Gateway

A reverse proxy with extra responsibilities — authentication, rate limiting, routing to microservices. The right term to use in microservices-flavored design questions.

Interview Angle
Recognition signal If you've drawn a load balancer or CDN in your design — you've already used a reverse proxy. Recognizing that connection unprompted shows a coherent mental model, not just memorized component names.
Clean one-liner to have ready "A forward proxy hides the client from the server. A reverse proxy hides the server from the client." This distinction is asked directly fairly often.
Quick Revision Recap
Forward proxy = represents client. Server doesn't see the real client. (Anonymity, access control, outbound caching.)
Reverse proxy = represents server. Client doesn't see real backend. (LB, TLS termination, caching, hide topology.)
Every load balancer and CDN edge node IS a reverse proxy — not a separate concept.
API Gateway = reverse proxy + auth + rate limiting + service routing. Key term for microservices designs.
⟳ Availability is the goal that load balancers, clustering, caching, and CDNs all serve. It's also one half of the CAP theorem trade-off — availability vs consistency.
Core Concept

Availability = is the system up and able to respond when someone tries to use it? Expressed as a percentage of uptime. A highly available system is designed to keep working even when individual parts fail — because in any large distributed system, something is always failing somewhere.

The Nines
AvailabilityDowntime / year
99%~3.65 days
99.9%~8.7 hours
99.99%~52 minutes
99.999%~5 minutes

Each additional nine is dramatically harder and more expensive — often requiring a fundamentally different architecture.

SLI / SLO / SLA
SLI (Service Level Indicator)

The actual measured metric — e.g., "% of requests that succeeded in the last 30 days."

SLO (Service Level Objective)

Internal target for the metric — e.g., "we aim for 99.9% success rate."

SLA (Service Level Agreement)

External/contractual promise — usually looser than the SLO, so you breach your internal goal before breaching a paying customer's contract.

How Availability Is Achieved
  • Redundancy — no single component is the only thing keeping the system up
  • Failover — automatic traffic shift on failure (heartbeats + leader election from Clustering topic)
  • Eliminate SPOFs — systematically remove every "if this dies, everything dies" component
  • Graceful degradation — partial functionality survives, instead of a total outage
  • Multi-AZ / multi-region — spread infra across physically separate data centers
CAP Theorem (brief)

In a distributed system, during a network partition, you must choose between:

ChoiceBehaviorGood forRisk
Favor AvailabilityKeeps serving, possibly stale dataSocial feed, DNS, cachesStale or conflicting data
Favor ConsistencyRefuses requests until consistentPayment systems, bankingAppears down during partition
Interview Angle
"Design a highly available X" prompt Walk through explicitly: redundancy at every layer (LB, app servers, DB), failover mechanism, SPOF elimination, multi-AZ deployment, graceful degradation. Don't just say "multiple servers."
CAP-flavored question "During a partition, would you return stale data or an error?" Answer based on domain: social feed → availability (show stale content). Payments → consistency (reject the request, don't risk double-charging).
Reframe availability correctly Not "the system never fails" — "designed to keep serving users despite individual component failures." That's the accurate and impressive framing.
Quick Revision Recap
Availability = % uptime, measured in "nines." Each additional nine is dramatically harder/costlier.
SLI = measured metric. SLO = internal target. SLA = external contractual promise (looser than SLO).
Achieved via: redundancy, failover, SPOF elimination, graceful degradation, multi-AZ/region.
CAP: partition forces choosing availability (keep responding, maybe stale) or consistency (correct, maybe down).
Netflix Chaos Monkey: deliberately kills prod servers to verify real resilience, not assumed resilience.
⟳ Scalability is the WHY behind load balancers, clustering, caching, and CDNs. "Design X for scale" frames almost every system design question you'll encounter.
Vertical Scaling (Scale Up)

Make the existing machine bigger — more CPU, more RAM, faster SSD.

  • Simple — no architecture changes needed
  • No distributed systems complexity
  • Hard ceiling — there's a maximum machine size
  • Gets disproportionately expensive near the top
  • Still a single point of failure
Horizontal Scaling (Scale Out)

Add more machines, distribute load across them — what load balancers and clustering enable.

  • Near-unlimited growth ceiling
  • Better fault tolerance (many small machines vs one big one)
  • Introduces distributed complexity — coordination, data partitioning, failure handling
  • Works best with stateless applications (any server can handle any request)
Scaling Reads vs Writes
Read scaling (the easier problem)

Most systems are read-heavy. Caching, CDNs, and read replicas handle this well with minimal architectural complexity.

Write scaling (the harder problem)

Can't just add unlimited copies of "the source of truth." This is exactly why sharding exists — splitting data across multiple databases each holding a slice.

Two Distinct Axes
Traffic scaling

More concurrent users/requests. Solution: more app servers + load balancing + caching.

Data scaling

More data than fits well on one machine. Solution: sharding/partitioning. A system can have huge traffic but small data (URL shortener) or modest traffic but huge data (analytics warehouse).

Trade-offs
ChoiceProsCons
Vertical scalingSimple, no distributed complexityHard ceiling, expensive, still a SPOF
Horizontal scalingNear-unlimited, better fault toleranceNeeds statelessness, coordination, data partitioning
Read replicas + cacheBig wins for read-heavy systemsDoesn't help write-heavy bottlenecks at all
Sharding (write scaling)Only real way past one machine's write limitComplex — cross-shard queries, rebalancing
Interview Angle
State your assumed scale early "Let's assume 1M daily active users, mostly read-heavy." This single sentence justifies every architectural choice that follows. Interviewers want to see you scope the problem, not design in a vacuum.
"Scale this 100x" question Walk the progression: vertical scaling first (quick, cheap) → horizontal (LB + more stateless app servers) → caching → read replicas → sharding if writes are the bottleneck. This progression shows maturity.
Trap Don't jump straight to sharding for every problem. Sharding is heavy and complex. Reach for caching and read replicas first, and only shard when writes are genuinely the bottleneck.
Quick Revision Recap
Vertical (bigger machine, ceiling, SPOF) vs Horizontal (more machines, near-unlimited, needs coordination).
Read-heavy → caching / read replicas solve most of it cheaply. Write scaling is harder → sharding.
Traffic scaling (concurrent load) vs data scaling (volume) — different problems, different solutions.
Scaling is iterative: find the current bottleneck, fix it, anticipate the next one. Not a one-time design.
State assumed scale early in any design answer — it justifies all your subsequent choices.
⟳ Storage sits below the database layer. Databases themselves run on block storage underneath. Object storage + CDN is one of the most common production pairings for media delivery.
Block Storage

Raw, fixed-size chunks of data — no metadata or file structure. The OS/application decides how to organize blocks into something meaningful. Extremely fast, low-latency.

  • Typically attached to a single server
  • Not naturally shared across many machines
  • Use case: databases, VM disks
  • Example: AWS EBS
File Storage

Familiar folder/file hierarchy, accessed via standard protocols (NFS, SMB). Multiple machines can mount the same filesystem like a shared network drive.

  • Easy multi-machine sharing
  • Familiar mental model (paths, directories)
  • Doesn't scale as well to massive distributed workloads
  • Use case: shared config files, legacy apps
  • Example: AWS EFS, NFS
Object Storage

Data stored as discrete objects: data + metadata + unique key. Flat namespace (no folders), accessed via simple HTTP API (GET, PUT, DELETE). Built for massive scale and durability, not low-latency random access.

Best for

Images, videos, backups, logs, static website assets — anything large and unstructured.

Examples

AWS S3, Google Cloud Storage, Azure Blob Storage. Common pairing: S3 + CloudFront (CDN).

Trade-offs
TypeProsCons
BlockFastest, fine-grained control, databases love itNot naturally shared across machines
FileFamiliar hierarchy, easy sharing via NFS/SMBDoesn't scale as well to massive distributed workloads
ObjectScales to unlimited, highly durable, cheap at scale, simple APIHigher latency, not built for frequent small in-place edits
Interview Angle

Core Concept

RAID combines multiple physical drives into one logical unit to achieve better performance, redundancy, or both. Individual disks are cheap and fail regularly — RAID uses multiple disks together to produce something more reliable or faster than any single one.

The key insight: you can combine drives in different patterns (RAID "levels"), each with a distinct trade-off between performance, redundancy, and how much usable storage you get.

RAID 5 and 6 use XOR-based parity to reconstruct a failed drive without a full mirror. Example:

Example

⟳ Databases sit on top of block storage (Storage + RAID topics). Redis straddles both cache and database. ACID directly determines your availability vs consistency trade-off (CAP theorem).
Core Concept

A database is an organized collection of structured data stored and accessed electronically. A DBMS (Database Management System) is the software layer between your application and the raw data — it handles storing, retrieving, updating, and managing data while enforcing consistency, access control, and concurrency.

Think of it this way: the database is the filing cabinet; the DBMS is the filing system, the locks on the drawers, the index tabs, and the person who manages who gets access to what.

Core DBMS Functions
  • Storage management — how data is physically laid out on disk (block storage underneath)
  • Query processing — parse SQL, optimize execution plan, execute and return results
  • Transaction management — all-or-nothing groups of operations via ACID
  • Concurrency control — multiple clients reading/writing without corrupting data (locks, MVCC)
  • Crash recovery — write-ahead log (WAL) lets the DB recover to a consistent state after a crash
  • Access control — authentication and authorization for who can see/modify what
ACID Properties
Atomicity

A transaction is all-or-nothing. If one step fails, the whole transaction rolls back. No half-completed bank transfers.

Consistency

A transaction brings the DB from one valid state to another — can never violate defined constraints or foreign keys.

Isolation

Concurrent transactions don't interfere with each other. Each sees a consistent snapshot as if it ran alone. Different isolation levels trade off strictness vs performance.

Durability

Once committed, data stays committed — even if the server crashes immediately after. Enabled by the write-ahead log (WAL).

How a Query Executes
StepWhat happens
1. ParserChecks syntax, validates that table/column names exist
2. Query OptimizerGenerates multiple execution plans, picks the cheapest one based on statistics and available indexes
3. Execution EngineFetches pages from disk or buffer pool, applies filters, joins, aggregations
4. ResultsReturned to the client
Indexes

A separate data structure (usually a B-tree) mapping column values → rows so the DB doesn't scan every row. Fast reads, slower writes (every write must update the index too), extra storage. This is the core read/write trade-off in miniature — over-indexing hurts write-heavy workloads.

MVCC (Multi-Version Concurrency Control)

Readers and writers don't block each other. Readers see the "old" version of a row while a write is in progress. Used by PostgreSQL and others to dramatically improve concurrency without locking the entire row for reads.

⟳ SQL = ACID by default, vertical scaling. NoSQL = BASE/eventual consistency, horizontal scaling. Your DB choice determines your consistency model and scaling story.
Core Concept

SQL (Relational): structured tables, predefined schema, foreign keys, joins, queried with SQL. Strong ACID guarantees. Optimised for correctness and query power.

NoSQL: an umbrella for any DB not using the relational model. Each type optimised for a specific data model and access pattern. Optimised for flexibility and horizontal scale.

The core difference is the data model — not just the query language. SQL optimises for data integrity and query power. NoSQL optimises for flexibility and scale.

SQL — Relational Model
  • Tables — predefined columns with types, each row is a record
  • Foreign keys + JOINs — relationships enforced by the DB
  • Rigid schema — every row must match the same column structure
  • Normalisation — data split across tables to eliminate redundancy

Key-Value (Redis, DynamoDB)

Giant hash map. Lookup by key only. Extremely fast. Limited — no range queries on values.

Wide-Column (Cassandra, HBase)

Dynamic columns per row, massive write throughput, distributed by design.

Graph (Neo4j)

Nodes + edges + properties. Optimised for relationship traversal — orders of magnitude faster than recursive SQL JOINs.

⟳ Replication = copies of the same data on multiple machines. Solves read scaling + availability. Does NOT help write throughput — that requires sharding.
Core Concept

Replication keeps copies of your database on multiple machines, automatically synchronised. One machine handles writes, others serve reads and act as failover targets. Solves two problems: a single database is a performance bottleneck (everything through one machine) and a single point of failure (it dies, your data layer goes down).

Primary-Replica Model
  • Primary (leader/master) — accepts all write operations
  • Replicas (followers/read replicas) — receive copy of every write, serve reads
  • Writes always go to primary. Reads can go to either.
How changes propagate
  • Statement-based — SQL statement sent to replicas; risky with non-deterministic functions (NOW(), RAND())
  • Row-based — actual changed rows sent; reliable, larger log
  • WAL shipping — primary ships its write-ahead log; used by PostgreSQL, very reliable
Sync vs Async Replication
Asynchronous (most common)

Primary commits and returns success immediately, without waiting for replicas. Low write latency but replication lag — replicas slightly behind. Risk: data loss if primary dies before replica catches up.

Synchronous

Primary waits for at least one replica to confirm receipt before returning success. No data loss on primary failure. Cost: higher write latency, primary blocks if replica is slow/unreachable.

Semi-synchronous

Waits for at least one replica — not all. Balances durability guarantee with not being blocked by every slow replica.

Replication Lag & Failover
Replication Lag

Time delay between write on primary and visibility on replica. A client writing to primary then reading from replica may see stale data. Fix: read-your-own-writes consistency — route reads immediately after a write back to the primary.

Failover

Primary dies → monitoring detects via heartbeats → most up-to-date replica promoted via leader election (Patroni for Postgres, MHA for MySQL) → connections rerouted via virtual IP or proxy. Old primary rejoins as a replica — never as primary — to avoid split-brain.

Sync replicationNo data loss, replica always currentHigher write latency, blocked if replica slow/unreachable
Multi-primaryHigher write throughputWrite conflicts — complex and error-prone
More replicasMore read capacity, more failover optionsMore replication propagation lag, more cost

Critical trap — know this cold Replication does NOT help write throughput. Every replica still processes every write from the primary — it copies all writes, doesn't distribute them. Write scaling = sharding, not replication.
Stale read question "User writes data and immediately reads it back but gets stale data" → replication lag + read went to a replica that hadn't caught up. Fix: read-your-own-writes routing back to primary.

⟳ Indexes are the difference between a 50ms query and a 50-second query on the same data. The trade-off: faster reads, slower writes. Over-indexing kills write-heavy tables.
Core Concept

An index is a separate data structure maintained alongside your table that lets the database find rows without scanning every single row. Like the index at the back of a textbook — extra work to maintain, but saves enormous lookup time. Without indexes, every query does a full table scan — catastrophically slow at scale.

Index Types
B-Tree (default)

Sorted tree. O(log N) lookups. Supports equality, range queries, and sorting. The default index type in almost every database. Values stored in sorted order so range queries scan forward from start of range.

Hash Index

Hash map: column value → row pointer. O(1) for exact equality. Useless for range queries or sorting — no concept of "greater than" in a hash map.

Full-Text Index

Inverted index mapping each word → every row containing it. Enables fast text search. Elasticsearch is an entire engine built around this concept.

Composite & Covering Indexes
Composite Index (multi-column)

Index on more than one column, e.g. (last_name, first_name). The critical rule: leftmost prefix rule — the index can only help queries that filter on the leading columns.

  • WHERE last_name = 'X' ✓ uses index
  • WHERE last_name = 'X' AND first_name = 'Y' ✓ uses index
  • WHERE first_name = 'Y' ✗ skips leftmost — can't use index
Covering Index

Index contains ALL columns the query needs — DB never touches the actual table rows. Maximum read speed, zero row lookups.

⟳ Sharding splits data across machines (each shard = unique subset). Replication copies the same data everywhere. Sharding solves write scaling — the problem replication cannot fix.
Core Concept

Sharding splits your database horizontally across multiple independent machines, each holding a distinct subset of the data (a shard). Shard 1 holds users 1–1M, shard 2 holds 1M–2M, etc. Each shard is an independent database, unaware of the others.

The critical distinction: replication copies ALL data to every node. Sharding gives each node a UNIQUE slice. Replication = read scaling + availability. Sharding = write scaling + data volume scaling.

Shard Key — The Most Critical Decision

The column used to determine which shard a row lives on. A bad shard key is extremely painful to undo.

Properties of a good shard key
  • High cardinality — many distinct values
  • Even distribution — rows spread evenly, no hotspots
  • Query alignment — most queries filter by the shard key
  • Immutable — never changes (changing = moving the row to a different shard)
Sharding Strategies
Range-based

Rows assigned by key value ranges. Simple, good for range queries. Risk: hotspots if data isn't uniformly distributed.

Hash-based

shard = hash(key) % N. Even distribution. Range queries hit all shards. Resharding problem: adding a node remaps ~(N-1)/N of keys.

Consistent Hashing

Keys and nodes mapped to a ring. Adding a node moves only ~1/N of keys. Used by Cassandra, DynamoDB. The solution to the resharding problem.

Directory-based

Lookup table maps key → shard. Maximum flexibility. The directory itself becomes a SPOF/bottleneck.

Cross-Shard Complexity
ProblemWhat happensSolution
Cross-shard queriesQuery must hit every shard, results aggregated — scatter-gather pattern. Slow.Design data model so common queries fit on one shard
Cross-shard JOINsCan't JOIN natively across shards — must fetch from multiple and join in app layerDenormalise; keep related data on the same shard
Cross-shard transactionsACID across shards requires 2PC — complex, slow, new failure modesDesign to avoid cross-shard transactions entirely
HotspotsOne shard gets disproportionate traffic (celebrity user, viral event)Random key suffix; dedicated shard for hot keys
Interview Angle
Escalation order — this matters Caching → read replicas → vertical scaling → sharding as last resort. Jumping straight to sharding for a small-scale problem is an immediate red flag.
"How do you add a shard without downtime?" Consistent hashing — only ~1/N of keys need to move. With naive hash % N, nearly everything moves. This is exactly why consistent hashing was invented.
Sharding pushes complexity to the application Cross-shard JOINs, scatter-gather queries, distributed transactions all move from the DB layer into your application code. This is a cost teams often underestimate.

⟳ Normalisation = data integrity, write correctness. Denormalisation = read performance. Most production systems live somewhere between the two extremes.
Normalisation

Organising data to eliminate redundancy — each piece of information exists in exactly one place, relationships via foreign keys. Strong consistency, easy updates. Many JOINs needed for reads.

1NF — Atomic values

No lists/arrays in a column. Each row uniquely identifiable. Bad: phone_numbers = "555-1234, 555-5678". Fixed: separate user_phone_numbers table.

2NF — No partial dependencies

Every non-key column depends on the ENTIRE primary key (matters for composite keys). Bad: order_items(order_id, product_id) stores product_name — depends only on product_id. Fixed: move to products table.

3NF — No transitive dependencies

Non-key columns depend only on the primary key, not on each other. Bad: users table has both zip_code and city — city depends on zip_code, not user_id. Fixed: separate zip_codes table.

Denormalisation

Deliberately reintroducing redundancy to speed up reads. Faster reads, simpler queries, fewer JOINs. Risk: update anomalies — same data in multiple places, update one and forget the other.

Storing derived/redundant columns

Add order_total to orders even though it could be computed by summing order_items. Saves aggregation on every read.

Duplicating columns across tables

Store user_email directly in orders alongside user_id. Avoids JOIN to users. Risk: email changes in two places.

Pre-computed aggregation tables

Maintain user_order_counts updated on every order insert/delete. Reads become simple lookups instead of expensive COUNT queries.

The Order Snapshot Pattern — Justified Denormalisation

At order creation time, snapshot the product name, price, and description directly into the order_items row — even though those fields exist in products. Products change over time (price increases, name changes), and you need the order to reflect what was true at the time of purchase, not today's data. This is deliberate, justified denormalisation — a perfect interview example.

OLTP (Online Transaction Processing) = transactional, operational, usually normalised. OLAP (Online Analytical Processing) = analytical queries, usually denormalised/star schema. Know these terms — interviewers use them to signal which type of system is being discussed.

⟳ ACID = correctness above all (SQL). BASE = availability + performance above strict correctness (NoSQL). The choice is always driven by what the business can afford to get wrong.
ACID
Atomicity — all-or-nothing

If one step fails, the whole transaction rolls back. No partial updates. Implemented via WAL — on crash, replay to complete or roll back in-flight transactions.

Consistency — valid state → valid state

Transactions can never violate defined integrity rules (constraints, foreign keys). Not the same as CAP consistency — ACID = integrity rules enforced. CAP = all nodes see same data simultaneously.

Isolation — concurrent txns don't interfere

Each transaction sees a consistent snapshot as if it ran alone. Implemented via isolation levels — a dial between correctness and performance.

Durability — committed = permanent

Survives crashes. Implemented via WAL flush to disk before commit acknowledged. Relaxing this (synchronous_commit=off) improves throughput at risk of losing last few transactions.

BASE
Basically Available

System always responds — even during partitions or failures. Response might not be freshest data, but you get something rather than an error. This is the availability side of the CAP trade-off.

Soft State

System state may change over time without new input — replicas catching up, nodes syncing. No guarantee that two reads in a row return the same value.

Eventually Consistent

Given enough time with no new writes, all nodes converge to the same value. The inconsistency window = replication lag. Data is correct eventually, not immediately.

Eventual consistency flavours
  • Read-your-own-writes — always see your own most recent write
  • Monotonic reads — never see an older version than you've already seen
  • Causal consistency — causally related ops seen in correct order

LevelPreventsAllowsPerformance

Anomaly definitions
  • Dirty read — reading uncommitted data that may get rolled back
  • Non-repeatable read — same row, different value on re-read (another txn modified it)
  • Phantom read — same query, different rows on re-run (another txn inserted/deleted rows)
Interview Angle
ACID consistency ≠ CAP consistency — a very common trap ACID consistency = data integrity rules always enforced (constraints, foreign keys). CAP consistency = all nodes see the same data at the same time. These are completely different things sharing the same word. Getting this right is a strong signal.
"Which for payments vs social feed?" Payments → ACID (losing money or double-charging is catastrophic). Social feed → BASE-tolerant (slightly stale data acceptable, ACID at this scale is too expensive). Always justify by what the business can afford to get wrong.
Don't say BASE = unreliable BASE systems are highly available and durable — they just don't guarantee every read returns the absolute latest value. It's a deliberate engineering trade-off, not sloppiness.

⟳ CAP is the theoretical backbone of replication lag, BASE vs ACID, and sharding. P is non-negotiable in real distributed systems — the real choice is CP vs AP.
Core Concept

A distributed data system can only guarantee two of three simultaneously: Consistency (all nodes see the same data), Availability (always responds), Partition Tolerance (survives network failures).

The key nuance most candidates miss: Partition Tolerance isn't a real choice. Networks fail in any real distributed system. So the actual trade-off is always: during a partition, do you sacrifice Consistency or Availability? CAP is really CP vs AP.

CP Systems

Consistency + Partition Tolerance. During a partition, refuses to serve requests rather than risk returning stale data. Clients see errors/timeouts. When partition heals, resumes with guaranteed consistency.

  • Good for: banking, inventory, leader election — wrong data is worse than no data
  • Examples: HBase, ZooKeeper, etcd, clustered PostgreSQL, Redis (Sentinel)
AP Systems

Availability + Partition Tolerance. During a partition, keeps serving requests using whatever data it has, even if stale. No errors — clients always get a response. Nodes reconcile and converge when partition heals.

  • Good for: social feeds, product catalogues, user sessions, DNS — temporary staleness acceptable
  • Examples: Cassandra, DynamoDB, CouchDB, DNS

PACELC — Beyond CAP

CAP only describes behaviour during a partition. PACELC extends it: If Partition → A vs C (same as CAP). Else (normal operation) → Latency vs Consistency. Even without a partition, synchronous replication (strong consistency) has higher latency than async (eventual consistency). The trade-off never disappears — it just changes shape.

Tunable Consistency (Cassandra / DynamoDB)

Choose consistency level per operation: ONE (max availability, possible staleness) | QUORUM (majority agree, balanced) | ALL (max consistency, lowest availability). Make the CP/AP trade-off per query, not globally.

Interview Angle
"CP or AP for this system?" Anchor on: "What's worse — serving stale data or returning an error?" Financial systems → CP. Social/content systems → AP. Then name a database that fits and justify it.
CA is not a real distributed option A CA system is just a single-node system. The moment you distribute it, partition tolerance becomes mandatory and you're back to CP vs AP. Never present CA as a valid distributed architecture choice.
Name-drop PACELC Mentioning PACELC signals you know CAP's limitations — the latency/consistency trade-off exists during normal operation too, not just during failures. Most interviewers will be impressed by this.

⟳ Consistent hashing solves the resharding problem from DB Sharding topic. Cassandra's token ranges ARE consistent hashing. Used in caches, CDNs, load balancers, and WebSocket routing.
Core Concept

Consistent hashing distributes data/requests across a dynamic set of nodes such that when nodes are added or removed, only ~1/N of keys need to be remapped — not ~(N-1)/N like naive hashing.

The problem it solves: hash(key) % N works fine when N is fixed. Change N by one node and nearly every key maps to a different node — catastrophic for live systems with millions of keys.

The Naive Hashing Problem

3 nodes, key % 3: user:1→Node2, user:2→Node1, user:3→Node0. Add 4th node, key % 4: user:1→Node1, user:2→Node2, user:3→Node3. All three keys moved. At scale: adding 1 node to a 10-node cluster remaps ~90% of all keys → cache miss storm or full data migration.

The Hash Ring
  • Both keys and nodes hashed onto a circular ring (0 to 2³²)
  • Each key assigned to the first node clockwise from its position
  • Adding a node: only keys between the new node and its predecessor move (~1/N)
  • Removing a node: only its keys move to the next clockwise node (~1/N)
Virtual Nodes — Solving Uneven Distribution

Basic consistent hashing with few nodes gives uneven distribution — nodes land at arbitrary positions on the ring, some get large slices, some get small ones.

Solution: Virtual Nodes (vnodes)

Place each physical node at multiple positions on the ring (e.g., 150 virtual nodes per physical node). Benefits:

  • Distribution becomes near-uniform — each node gets many small evenly-spread slices
  • When a node is added, it takes a small amount of load from many nodes — smoother rebalancing
  • When a node is removed, its load spreads evenly across all remaining nodes

This is exactly how Cassandra implements sharding — every node owns multiple token ranges (virtual nodes) on the ring. DynamoDB uses a similar approach.

⟳ Local transactions = single DB, DBMS handles everything. Distributed = spans multiple systems, no shared coordinator. The jump in complexity is enormous — design to avoid it where possible.
Local Transaction

Single database. Application issues BEGIN → operations → COMMIT or ROLLBACK. DBMS handles locking, isolation, crash recovery via WAL. Straightforward — one system in control.

Why distributed is hard

Two independent systems — payment service and inventory service, each with their own DB. What if payment commits but network dies before inventory gets the signal? What if inventory's DB crashes mid-transaction? There's no shared coordinator, no shared WAL, no single system in control.

Two-Phase Commit (2PC)

Classic protocol for distributed transactions. A coordinator manages two phases:

Phase 1 — Prepare (Voting)

Coordinator sends PREPARE to all participants. Each checks if it can commit, acquires locks, writes to WAL but does NOT commit. Responds YES or NO.

Phase 2 — Commit or Abort

ALL said YES → coordinator sends COMMIT to all. ANY said NO → coordinator sends ABORT to all.

⚠ Problems with 2PC
  • Blocking: coordinator crashes after PREPARE but before COMMIT → participants hold locks indefinitely
  • Slow: two network round trips before anything commits
  • SPOF: coordinator is a bottleneck and single point of failure
  • CP only: not partition tolerant — partition stalls the whole transaction
The Saga Pattern

The most widely used alternative to 2PC in microservices. Breaks the transaction into a sequence of local transactions, each with a compensating transaction that undoes its effect if something later fails.

Choreography-based

No central coordinator. Each service publishes an event on completion. Others listen and trigger next step. Loosely coupled but harder to trace failures.

Orchestration-based

Central orchestrator tells each participant what to do and handles failures. Easier to debug — single source of truth. Tighter coupling.

Outbox Pattern

Solves: how do you atomically update your DB AND publish an event to a message queue without a distributed transaction between them?

The problem

Service commits to DB, then crashes before publishing to Kafka. Downstream services never know the transaction happened.

The solution

Write the event to an outbox table in the same local DB as part of the same local transaction. A separate relay process reads and publishes unpublished events. DB write + event are committed atomically — event is never lost.

Idempotency

Distributed systems retry constantly. Without idempotency, retries cause duplicates.

Idempotent vs Non-idempotent
  • SET balance = 500 ✓ idempotent — same result if run twice
  • balance = balance + 50 ✗ NOT idempotent — adds 100 if run twice
Idempotency keys

Caller generates a unique UUID per operation. Receiver checks if it has already processed this key — if yes, returns cached result. If no, processes and stores result. This is why Stripe requires an Idempotency-Key header on every payment — a retry after timeout doesn't double-charge.

Interview Angle
"Transaction spanning two microservices?" Don't jump to 2PC. Present the options: 2PC (strong consistency, blocking, CP) vs Saga (eventual consistency, available, AP). Pick based on consistency requirements — Saga is almost always the right call for microservices.
Strong differentiator: Outbox Pattern Most candidates who know Sagas don't know the Outbox Pattern. Proactively mentioning it — "to reliably publish events after a local commit without a distributed transaction between DB and queue" — is a strong differentiator.
Idempotency keys Whenever retries come up, mention idempotency keys. Stripe's implementation is a concrete, recognisable real-world example. Distributed systems retry constantly — without idempotency, retries cause duplicates.

2PC: Coordinator sends PREPARE (participants say yes/no) → COMMIT/ABORT. Strong consistency but blocks if coordinator fails. CP, slow, SPOF.
Saga: sequence of local transactions with compensating transactions. Failures trigger compensating txns in reverse. Eventual consistency, high availability, AP.
